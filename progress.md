- **Smart App Control на рабочей машине владельца блокирует нативный `satteri`** (Markdown-процессор Astro 7, `@astrojs/markdown-satteri`): `An Application Control policy has blocked this file … satteri_napi.win32-x64-msvc.node`. Остальные нативные модули (rolldown, sharp, lightningcss, компилятор Astro) грузятся. Обход — только локальный: после каждого `npm ci` / `npm install` (включая `npm install -D <пакет>`: он тоже удаляет обход, ep01 T04) выполнить `npm install --no-save --force @bruits/satteri-wasm32-wasi@<версия satteri из npm ls satteri>`. Загрузчик satteri сам падает на WASI-сборку, если нативная не загрузилась. `package.json` и `package-lock.json` не меняются, в CI (Linux) грузится нативная сборка. Симптом без обхода: `astro check` / `vitest` / `astro build` падают с `Cannot find native binding`. (ep01 T02)
- **В Windows-окружении нет `python`** — скриптовые правки файлов делаются через `node`. (ep01 T01)
- **`tsconfig.json` исключает `docs`**: иначе `astro check` проверяет JS дизайн-источников в `docs/inputs/` и шумит подсказками. (ep01 T02)
- **Две ступени токенов**: примитивы ДС — `src/styles/tokens/*.css` (копия без изменений, тест `contrast.test.ts` сверяет со снимком `tests/fixtures/ds-sources.json`, снимок с `docs/inputs/…` — `ds-sources.test.ts`); семантика — только `src/styles/theme.css`. Имена семантики не повторяют имена примитивов (`--radius-sm` занят ДС → `--radius-field`; `--space-1…9` → `--space-2xs…2xl`), иначе `var()` зацикливается. Компоненты используют только семантику. (ep01 T03)
- **`sharp()` не принимает `URL`**: в скриптах путь из `new URL(…, import.meta.url)` передаётся через `fileURLToPath`. (ep01 T05)
- **`Logo.astro` — единственная точка вывода знака**: `size` — высота в CSS px, предел — половина исходника (`src/lib/logo.ts`); обязателен `alt` либо `decorative`. Фавиконки пересобираются `npm run build:favicons` и коммитятся. (ep01 T05)
- **Id записи контента = путь файла без `.md`**: коллекции на `glob` в `src/content.config.ts` задают `generateId` по пути. Стандартный slugify понижает регистр и учитывает `slug` из frontmatter и прячет нарушения формата id от `assertContentIntegrity`. Новые коллекции — через тот же хелпер `markdown(base)`. (ep01 T06)
- **Схемы с `image()` — фабрики** в `src/lib/schemas.ts` (`pageSchema(image)`, `siteSchema(image)`); в тестах `image` подменяется на `() => z.string()`, `reference()` — на `z.string()`. `astro:*` в `schemas.ts` не импортируется. (ep01 T06)
- **Видимая высота знака — токен, `size` у `Logo` — разрешение растра.** Предок задаёт `--logo-height: var(--logo-…-h)` (токены в `theme.css`), `Logo.astro` берёт её, иначе высоту растра (`--logo-size`). `size` должен быть не меньше максимума токена, иначе знак растягивается. Так lockup заглушки ужимается до 360px без горизонтального скролла. (ep01 T08)
- **Страницы — через `Base.astro`**: `title` (готовая строка), `description`, `draft` (маркер `<html data-draft>` в любом окружении + плашка там, где черновики видны), `brandScreen` (страница сама показывает знак и слоган крупно: шапка без знака, подвал без имени и слогана). Раскладка — `.container`, надзаголовок — `.eyebrow` из `global.css`. (ep01 T08)
- **Скрипты-гейты в `scripts/*.mjs`** — `// @ts-check` + JSDoc (их проверяет `astro check`, отдельный `tsc` не нужен); логика — экспортируемая чистая функция, CLI — обёртка под `if (process.argv[1] && resolve(process.argv[1]) === fileURLToPath(import.meta.url))`, код 1 — нарушения, 2 — неверный вызов. Тесты импортируют функцию и правят копию фикстуры во временном каталоге (`mkdtempSync` + `cpSync`), CLI проверяют через `spawnSync(process.execPath, …)`. Пример — `check-dist-seo.mjs`. (ep01 T16)
- **Правила окружения сборки — в `src/lib/site-env.ts`** (`indexable`, `robotsTxt`, `sitemapEnabled`, `sitemapPageFilter`): компоненты и эндпоинты берут `SITE_ENV` из `astro:env/server` и не сравнивают его со строками сами. (ep01 T16)
- **Stylelint (`npm run lint:css`)**: литералы цвета, `rgb()`/`hsl()`/`color-mix()` и `px|rem|em|ms|s` в размерах, отступах, радиусах, движении — только в `src/styles/tokens/**` и `theme.css`; в компонентах — `var(--…)`, `0`, `%`, `fr`, `vw`, `vh`, безразмерный `line-height`, литералы в условиях `@media`. Охват — любые размеры (`width`/`height` с `min-`/`max-`, `*-size`, `flex`, `grid-template-*`), шорткаты `border`/`outline`/`font`, `transform`/`translate` и кастомные свойства `--…` вне слоя темы; фиксирует `tests/stylelint-tokens.test.ts` (/my-verify ep01, F03 Codex). Классы — kebab-case с BEM (`block__element--modifier`), `@import` — строкой, hex — шестью знаками. Примитивы в `tokens/**` не переформатируются (дословная копия ДС). (ep01 T22)
- **Симлинки в Git Bash**: `ln -s` по умолчанию копирует, нативные симлинки без режима разработчика запрещены. Shell-тесты с симлинками под `MINGW*|MSYS*` выставляют `MSYS=winsymlinks:sys` (эмуляция MSYS с настоящей семантикой `-L`/`readlink`/`mv -T`); на Linux не нужно. Пример — `infra/deploy/tests/belka-deploy.test.sh`. (ep01 T11)
- **Shell-скрипты в `infra/`**: `set -euo pipefail`, `LC_ALL=C`, `shellcheck` без замечаний, режим `100755` в git (`git update-index --chmod=+x`), LF (`.gitattributes`). shellcheck на машине владельца — из winget (`koalaman.shellcheck`); если оболочка открыта до установки, он лежит в `%LOCALAPPDATA%\Microsoft\WinGet\Packages\koalaman.shellcheck_…\shellcheck.exe`. (ep01 T11)
- **Два репозитория в одной рабочей папке** (с 2026-09-24): корень — публичный код `belka-site`, `docs/` — отдельный git приватного `belka-site-docs` (корень игнорирует `docs/`). Задача с правками кода и `tasks.md`/`log.md` — по коммиту в каждом, сообщение одно и то же. Код не читает `docs/` в тестах и сборке: исходники ДС — снимок `tests/fixtures/ds-sources.json` (значения примитивов и SHA-256 растров), его сверку с `docs/inputs` делает `tests/ds-sources.test.ts` при наличии `docs/`. Обновление ДС — скопировать файлы в `src/`, пересобрать снимок, `npm run check:docs`. Черновики текстов — в `docs/`, в `src/content/` только утверждённое. (ep01, разделение перед сессией F)
- **`npm run check:docs`** — локальный гейт документов: lychee офлайн по `docs/**/*.md`, `CLAUDE.md`, `progress.md` и сверка снимка ДС с `REQUIRE_DOCS=1`. Запускается pre-commit-хуком `docs/.git/hooks/pre-commit`; хук не версионируется, после клонирования `belka-site-docs` его ставят заново. lychee — из winget (`lycheeverse.lychee`). (ep01)
- **Итог гейтов — задание `gates-ok` в `gates.yml`** (required check `gates / gates-ok`, `app_id` GitHub Actions): `needs` на все задания гейтов, `if: always()` и явное падение, если хоть один результат не `success`. Задание, пропущенное из-за упавшего `needs`, GitHub засчитывает required check как успех. Новый гейт добавляется в `needs`, имя проверки не меняется. У шагов гейтов условий, `continue-on-error` и `|| true` нет. (ep01 T10)
- **Push в GitHub — через `gh`, а не Git Credential Manager**: в `.git/config` обоих репозиториев `credential.https://github.com.helper` сброшен и равен `!gh auth git-credential` (`username = petrorossolov-rgb`). Перед push — `gh auth status`: активен `petrorossolov-rgb`. `main` защищён, изменения — только веткой и PR. (ep01 T10)
- **Merge PR на стороне GitHub подписывается почтой аккаунта** — при любом способе: merge-коммит и squash ставят её в автора, rebase — в коммитера. Локальный noreply-адрес на это не влияет. Поэтому у `petrorossolov-rgb` включено «Keep my email addresses private» (Settings → Emails; через API не задаётся, нужен скоуп `user`). С ним веб-операции подписываются noreply-адресом. PR мёржится `gh pr merge <N> --rebase`: в истории остаются коммиты задач без merge-коммитов. После каждого merge — `git log -3 --format='%h %ae %ce' origin/main`: только noreply-адреса. Если там появилась настоящая почта, значит, настройка слетела: остановиться и сообщить владельцу. (ep01 T23, исправлено в сессии F)
- **Lighthouse CI**: `lighthouserc.{mobile,desktop}.cjs` строятся из `lhciConfig()` в `lighthouserc.base.cjs`; страницы — из sitemap прод-сборки плюс `/404.html` (`scripts/lhci-urls.mjs`), ручного списка нет. Запуск — `npm run lhci:mobile|lhci:desktop` на `dist/` прод-сборки. Третий параметр `lhciConfig(profile, settings, distDir = './dist')` — для тестов на фикстуре `tests/fixtures/dist-production/`: в `gates.yml` тесты идут до сборки (/my-verify ep01). - **nginx belkascm: все `add_header` — на уровне `server`**, в наших `location` своих нет: `add_header` в `location` отменяет унаследованные заголовки безопасности. Различия по пути — через `map` в контексте `http` (`infra/nginx/belkascm-maps.conf`, пример — `$belkascm_cache_control`), заголовок — `add_header … $переменная always` в сниппете. Сниппеты — `/etc/nginx/snippets/belkascm/`. HTTPS-версии конфигов ссылаются на `/etc/letsencrypt/live/<имя>/`, поэтому сертификат выпускается (`certbot certonly --webroot`, сначала `--dry-run`) до их установки. (ep01 T15)
- **Проверки с секретами не печатают команду**: `echo "### $*"` + `curl -u …` выводит пароль в журнал сессии. В таких проверках печатать только код ответа и заголовки. (ep01 T15)
- **Скрипты-проверки для workflow — в `infra/<назначение>/*.sh`**, а не шагами YAML: их прогоняют локально (Git Bash) и проверяет shellcheck в `gates.yml` (новый исполняемый файл `infra/`, в том числе без `.sh`, как `belka-deploy`, — в список шага «shellcheck скриптов infra»). Пороги — переменные окружения с дефолтом (`MIN_DAYS=400 bash infra/monitor/check-site.sh`), код 1 — проверка не прошла, 2 — неверный вызов. (ep01 T19)
- **Доставка — `deploy.yml` + `rollback.yml`, клиент сервера — `infra/deploy/ci-deploy.sh`, смоук — `infra/deploy/smoke.sh`.** Выкладывается artifact из прогона `gates` того же workflow; выкладка и смоук — шаги одного job с `environment:` (`concurrency: deploy-<env>` у обоих workflow). Промоушн вызывает `gates` с `site_env: staging` и `ref: <sha>` — те же гейты, что у стейджинга, плюс staging-`draft-routes.json` для проверки 404 черновиков на проде. Проверка «SHA на стейджинге» — успешный deployment `staging` (статус `success` ищется в истории: после следующей выкладки он становится `inactive`) **и** успешный push-прогон `deploy.yml`: `rollback.yml` тоже создаёт deployment, но с SHA запуска. Reusable `gates.yml` и `infra/deploy` в прогоне промоушна берутся из HEAD `main`, а не из SHA, поэтому SHA ≠ HEAD промоутится, только если между ними не менялись `.github/` и `infra/deploy/` (`infra/deploy/promote-guard.sh` по compare API, /my-verify ep01, F01 Codex). Смоук знает только инварианты окружения; с `--dist` тело `/` и 404 сверяется побайтно со сборкой. (ep01 T17, T18)
- **actionlint — через Docker**: `MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd -W):/repo" -w /repo rhysd/actionlint:latest -no-color` (в образе есть shellcheck для `run:`). В YAML `run: echo "…: …"` без блочного скаляра не парсится — двоеточие с пробелом; такие строки — через `run: |`. (ep01 T17)
- **Автоматический режим Claude не выполняет без явного «да» владельца в этой же сессии** `gh workflow run deploy.yml|rollback.yml` (выкладка в окружения) и, как правило, `gh pr merge` («Merge Without Review»; в сессии I первый merge прошёл, второй — нет). Эти шаги собираются в один список и подтверждаются владельцем заранее. (ep01 T17)

Клиентский JS или Метрика (ep05) — только осознанным расширением гейта с пограничной пробой, а не ослаблением (Constitution 4, 8). (ep01 T16, /my-sync-docs)
- **Пограничная проба гейта**: у каждого гейта есть проба не только на грубую поломку, но и на границу заявленного: агрегация (медиана, а не лучший прогон), охват правила (все свойства, которые обещает принцип), состояние, на котором гейт должен отказать (промоушн SHA ≠ HEAD). Проба — регресс-тест, который падает на мутанте с прежним поведением. Негативы T24 доказали только грубые случаи, а медиану Lighthouse, охват Stylelint и `promote-guard` нашёл `/my-verify`. - **SEO-слой — `src/lib/seo.ts` + `Seo.astro`**: страница передаёт в `Base` готовый `title` через `buildTitle(title, site.name, { home })` (у продукта — `productTitle`), `ogImage` из записи. - **Инструмент записи файлов Claude превращает escape-последовательности `\uXXXX` в сырые символы** — не только U+2028/U+2029, а любые (ep02 T02: `\u00A0`, `\u2009`, `\u202F`, `\uFFFC` в регулярках и строках стали невидимыми символами). U+2028/U+2029 ломают разбор TS/JS и Markdown; остальные работают, но исходник становится нечитаемым. Такие символы в коде — через `String.fromCharCode(0x2028)` либо escape-форму, вписанную после записи скриптом с `String.fromCharCode(92)`; проверка — `grep … | cat -A` (пример — `serializeJsonLd` в `src/lib/seo.ts`, регулярки `scripts/check-voice.mjs`). (ep01 T21, ep02 T02)
- **Линтер голоса — `scripts/check-voice.mjs`** (`parse5`): проверяет форму видимого текста собранного HTML (V1–V10) и `--text` — блоки ```` ```text ```` пакета черновиков (одна строка — один абзац). Текст собирается по блокам: строчные элементы (`INLINE`) склеиваются, всё остальное — граница; `script`, `style`, `code`, `pre`, `template`, `noscript`, `hidden` пропускаются; атрибуты `alt`, `aria-label`, `title`, `description`, текстовые `og:*` — отдельные блоки. Исключение — только `data-voice="raw"` в разметке, снимает V3, V4, V10. Границы слов для кириллицы — `(?<![\p{L}\p{N}])…(?![\p{L}\p{N}])` с флагом `u`: `\b` в JS кириллицу не видит. Флаг `i` вместе с `\p{Lu}` в JS совпадает и со строчными, поэтому регистр в V7 задаётся явно (`[Бб]`). Каждая граница правила держится тестом, проверено 44 мутантами. Смысл, факты и приватный чек-лист в код не попадают (Constitution 10). (ep02 T02)
